## 1. Архитектурный контракт
Life OS — единственный владелец планирования, задач, дат/времени, разрешений доставки, наблюдений и аналитики.
Persona — производит материал и его ревизии, исследует, делает дизайн, звук и адаптацию; не объявляет себя опубликованной.
Metricool/другой авторизованный адаптер — доставка/наблюдение, не владелец редакционной стратегии.
Эрика — координирует зависимости и блокеры, не подменяет источник истины. Dive M не смешивать с медиаконтуром.
Использовать существующие хранилища/очереди и адаптеры; не строить независимые параллельные системы. Контракт идентичности: contentId + revision + content/design fingerprint + SHA-256 rendered assets + destination/account scope + calendarSlotId + attemptId + externalReceipt. Раздельные состояния: редакция, производство, авторское решение, доставка, музыка, аналитика. Никакого одного глобального READY/PUBLISHED на основании одного флага.

## 4. Исполнительное задание Persona / Codex
Режим AUDIT_THEN_EXECUTE. Не создавать очередную систему и не начинать семь генераций до готового production gate. 
Этап A: read-only inventory точного head, сверить этот аудит со всеми текущими тестами, составить по каждому AUD-ID evidence/status/owner/affected paths, reproduction, proposed patch, test, rollback; если вывод опровергнут кодом — исправить отчёт. Запрещено ослаблять тесты ради зелёного CI.
Этап B: AUD-01/07 защита версии/данных, AUD-02 canonical calendar; изолированные коммиты/одна integration PR. Затем AUD-03/04 реальные исследования и дизайн; AUD-05/06 музыкальные и delivery gates. В первую очередь P0, не расширять feature list. Платные/внешние вызовы только после явного бюджета/разрешения; при отсутствии доступа — BLOCKED с точным требуемым входом, продолжить независимую работу.
Этап C: dry run с двумя настоящими разными материалами через всю цепочку, фактические файлы + hashes, источники, caption, 3 music candidates, destination manifests, раздельная приёмка. Авторская оценка и одна итерация исправления. Только затем 7 материалов: daily dates в Life OS, не переписывать уже опубликованное и запланированное. Каждый материал содержит (1) конкретную тему/смысл, (2) claim/source table, (3) 4–8 слайдов по смыслу, (4) exact PNG 1080×1350 и JPEG variant, (5) caption/short caption, (6) music brief, (7) Story draft, (8) revision + asset hashes, (9) independent QA receipt, (10) author-review status. Цель 7/7 действительных пакетов, не 7 обещаний. Если источники/изображения/музыка не готовы — пометить соответствующий материал BLOCKED, не выпускать в обход. 
Этап D: только после отдельного подтверждения автора — по платформам, с proof of publish и music state. Аналитика по фактическим публикациям, сравнимые окна. P1 ввести после базовой цепочки; реальный video QA отдельно. 
Обязательный отчёт после каждого этапа: exact commit, список файлов, команда и результат проверок, actual artifacts, данные/бюджет, статус PASS/PARTIAL/BLOCKED, причины, следующий проверяемый шаг. Не считать mocked API и synthetic media реальным принятием. Не merge main, не публиковать, не устанавливать платное/удалять файлы без разрешения. Не завершать миссию по количеству коммитов: измерять количество готовых материалов, повторяемость, фактическую долю ручных действий, отсутствие дубликатов и сохранность данных.

## 5. Измеримые release gates
G1 exact head CI, воспроизводимая версия + backup/restore. G2 единый daily calendar и устойчивый restart. G3 2 new source-backed materials, независимый фактчек и реальный PNG с авторской художественной приёмкой. G4 7/7 review-ready assets (нет автоматического design PASS), музыка и форматы готовы либо честно BLOCKED. G5 per-destination authorized dry run + real delivery when authorized; подтверждённая музыка отдельно. G6 сопоставимые наблюдения и регрессии Life OS/Erika, real-device review. 
Статус до G1–G6: PARTIALLY VERIFIED. Этот коммит содержит только аудит; ни одного исправления исходников, запуска модели, изменения расписания или отправки поста.
